# あとからの紐付けの承認 決定ログ

親の承認のあと、[touryou.md](touryou.md) の末尾に追記する（承認の方針は、利用者の判断 2 で A に決まった）。

**実装の状況**: 1 件目（採用した子の runtime の記録）は PR1 で実装済み。2 件目（Desktop の採用の承認）と 3 件目（承認待ちの置き場）は PR3 で、未実装。

## 2026-11-22 採用した子にも runtime を記録し、見張りと画面を属性で判定する

- **Decision**: `node_adopt` が記録する `node.created` に、採用の runtime（今は `cli`）を入れる。止まり検知・紐付けていない子・紐付けが外れているかもの見張りと、画面の開き方・安全面は、「起動の報告がある子」でなく、`runtimeOf` が `cli` の子を対象にする。開き方の `sessionRef` は、`node.adopted.sessionRef` も読む。
- **Rationale**: 採用した子は起動の報告がないので、いまは見張りと画面の「開き方」「安全面」の対象から外れている。採用した子だけ、止まっても知らされない。属性を正にすれば、採用の経路と spawn の経路が、同じ扱いになる。
- **Rejected alternatives**: 採用のときに、起動の報告（`launch` の done）を偽って記録する — 実際に起動していない記録を作ることになり、記録が真実でなくなる。見張りの条件に「採用した子」を足す — 判定が経路ごとに分かれ、Desktop の採用を足すときに分岐が増える。

## 2026-11-22 Desktop の子の採用は、人の承認を挟んでから結ぶ

- **Decision**: `node_adopt` の `runtime:"desktop"` は、受信箱に承認待ちを出し、人が画面（人間のトークン）で承認するまで、`node.created`・`node.adopted` を記録せず、フック設定の配置・引き出し・紐付けのコードの発行もしない。承認は一度きり・期限つきで、子・根のトークンでは押せない。`runtime:"cli"` の採用は、今のまま（親の統合ノードが、人の同意を会話で得て呼ぶ。承認待ちを挟まない）。
- **Rationale**: #145 の守りの考えは、「ほかの事実と組み合わせて身元を確かめ、権限が増える操作は人が確かめる」である。Desktop の子は、FR_014 が効かず、人・root のトークンのファイルを読める子で、結ぶと木の権限が実質的に広がる。CLI の採用は、範囲が親に収まり、フックが効く（権限が増えない）。採用のきっかけが統合ノードの会話だけだと、信頼できない文章に従った統合ノードが、弱い子を木に足せてしまう。
- **Rejected alternatives**: 両方の採用に承認を挟む — 権限が増えない CLI の採用の手順を、重くするだけになる。取り消せない操作と同じ端末の確認コード（`/dev/tty`）を使う — launchd 経由の daemon では通らない（`confirmationUnavailable`）。承認なし — 統合ノードの判断だけで、弱い子が増える。

## 2026-11-22 承認待ちの置き場は PR3 の設計で決める

- **Decision**: 承認待ちを、確認待ちの欄（メモリだけ・再起動で消える）に載せるか、記録に残すかは、PR3 の設計で決める。決めるまで、PR3 は始めない。
- **Rationale**: 記録に残すと、イベントの型が増え、古い版へ戻せなくなる（`node.adopted` の導入と同じ性質）。メモリだけなら、再起動で承認待ちが消えるが、親が採用を呼び直せば済む。
- **Rejected alternatives**: None considered
