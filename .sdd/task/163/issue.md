# 既存の作業ツリー（とそこで動くセッション）を、touryou の子ノードとして採用できるようにする（v0.1.6 に入れる）

関連: #159（CLI の子と Desktop の子を同じ木で混ぜ、あとから紐付ける。案 D の「後付けの紐付け」と重なる）

## 困りごと

- 子として紐付けるには、`node_spawn` で新しいノードを作る必要がある。`node_spawn` は、作業ツリーとブランチを新規に作る。
- すでに動いているセッション（`spawn.sh` や手作業で作った worktree で動くもの）は、そのままでは子にできない。完走させて次の波から使うか、作り直すしかなく、移行がしにくい。

## 確認した事実（v0.1.5 の配布物を読んで確認。動作は未検証）

- `child-bind.js` / `bind-code-file.js`: 紐付けは `{ nodeId, bindCode, cwd }` を `POST /v1/bind` に送る。daemon は cwd が「そのノードの作業ツリー」であることを確かめる（FR_006）。コードは、作業ツリーの `.git` の gitdir 内の `touryou-bind-code` に、daemon が書く。
- 既存の作業ツリーを、ノードとして登録（採用）する CLI・MCP の操作は見当たらない。

## 期待する動き

1. 既存の作業ツリー（パス・ブランチ）を指定して、ノードとして登録できる（例: `node_adopt` / `touryou adopt`）。
   - 検査: `repoRoot` の worktree であること。ブランチ。未コミットの変更の扱い。他のノードと重複しない。
   - scope（書き込み範囲・許可コマンド）は、親が明示して付ける（採用しても、権限が勝手に広がらない）。
2. 登録したら、既存のセッションから `child_bind` で紐付けられる（bindCode の出し直し。`node.bindCode` と同様）。
3. 既存セッションを紐付ける skill（例: `/touryou:adopt`）。手順を案内し、親・子の双方で誤操作を防ぐ。
4. 採用は監査に残る（誰が、どの作業ツリーを、どの scope で採用したか）。

## 受け入れ基準

- [ ] 既存の worktree を、検査のうえ、ノードとして登録できる。検査に落ちる作業ツリーは、理由と次の操作が出る。
- [ ] 採用したノードの scope が、親の指定を超えない。
- [ ] 採用後、既存セッションが `child_bind` で子になれる。
- [ ] 採用は監査に残る。
- [ ] 手順が docs と skill にある。
