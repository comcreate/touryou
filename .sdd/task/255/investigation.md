# #255 調査と設計案: 手の空いた CLI の子の紐付けが外れたとき、人に打たせず戻す

> 対象 issue: #255。コードは変えていない（読んだだけ）。実機では確かめていない。
> 書き方: **【事実】** は読んだコードの場所つき。**【推測】** はコードから読んだ結論で、実機で未確認。

## 0. 要約

- 手の空いた子が戻らなくなる一番の原因は、**「戻す動き」がすべて、子の AI が `child_bind`（または道具の呼び出し）をして始まる作りになっている**こと。MCP は自分から結び直しを始めない。
- 紐付けが外れる経路は 3 つ（§1）。このうち、人が打つまで止まるのは、**購読が途切れたまま 1 時間経って、daemon 側のトークンが idle で切れた場合**（§1-C）。切れたあとは、コードなしの結び直し（#145・#185）は仕様どおり通らず、`node_bindCode` で作業ツリーにコードのファイルが書かれても、**それを読んで使うのは子の AI が `child_bind` を呼んだときだけ**。手の空いた子は呼ばない。
- 推奨は **案 1（MCP が自分で戻す）＋ 統括の確認の道（案 3 の「新しい道具なし」の形）**。MCP が (a) 起動直後、(b) 紐付け待ちの間の定期の確かめ、で結び直しを自動で試す。コードのファイルが現れたら、MCP が自分で使う。コードのファイルは 0600・持ち主・daemon の ID の確認を、いまの `child_bind` と同じに通す。人間のロールだけの操作は増やさない。
- 実機で確かめる必要がある項目（§6）: SendMessage が手の空いた子を起こせるか、attach のあとの session_id、MCP が自分の受信箱のソケットに書くと手の空いたセッションが起きるか、背景のセッションが約 1 時間で止まるときに MCP のプロセスがどうなるか。

## 1. 紐付けが外れる・切れる経路（受け入れ基準 1）

### 前提となる仕組み【事実】

| 項目 | 場所 | 内容 |
|:--|:--|:--|
| 子のトークンの置き場 | `packages/mcp/src/node-credential.ts` `createNodeCredentialStore` | MCP のプロセスのメモリだけ。ファイル・環境変数には置かない（`child-bind.ts` 冒頭のコメント）。 |
| 紐付け待ちで開く | `packages/mcp/src/stdio.ts` `openPendingStdioSession` | 作業ツリーの印（`touryou-child`）があると、道具は `child_bind` と `whoami` だけ。入れ物は空で始まる。 |
| 紐付けを始める条件 | 同 `bind`（`child_bind` の本体） | 子の AI が `child_bind` を呼んだときだけ。MCP の起動時・定期の確かめには、結び直しを試す処理が**ない**（`bind` の呼び出し元は道具だけ）。 |
| 購読 | `stdio.ts` `startNotifications` の子の分岐、`node-subscriber.ts` | 入れ物が空の間は購読しない（`follow` が `subscribeWaitingForBind` を記録して戻る）。値が入れば購読を始める。 |
| daemon のトークンの期限 | `packages/daemon/src/api/credentials.ts` `expiredReason` | bind のトークンは、使わなければ `bindIdle`（既定 60 分）、発行から `bindAbsolute`（既定 24 時間）で切れる。判断待ち・done の子は、時計を進めない（`isIdlePaused`）。 |
| 「使った」に数えるもの | `docs/plugin.md` 206 行、`CHANGELOG.md` #208 の項 | 購読の接続と約 15 秒ごとの heartbeat。購読が張られている間は idle で切れない。 |

### 経路 A: MCP がつなぎ直された（`claude attach`・`/mcp` の Reconnect・MCP の再起動）【事実＋推測】

- 【事実】メモリのトークンが消え、紐付け待ちに戻る（`docs/plugin.md` 241 行、`CHANGELOG.md` #136・#145）。`follow(undefined)` で購読も止まる（`stdio.ts` の `follow`）。
- 【事実】daemon 側のトークンは有効なまま残る。親の知らせ（#209）は、この状態を「トークンは有効だが購読がない」として拾う（`packages/daemon/src/cli-watch.ts` `watchFindings` の `unsubscribed`。既定 15 分）。
- 【事実】結び直しの入口は、子の AI の `child_bind` の呼び出しだけ（`stdio.ts` 429〜434 行）。
- 【推測】attach のあとも `CLAUDE_CODE_SESSION_ID` が同じか未確認（`docs/manual-verification-checklist.md` A4-3）。違えば、コードなしの結び直しは通らない。

### 経路 B: daemon が 401 を返した（再起動のあとなど）【事実】

- #185 で、道具の呼び出し・購読のどちらの 401 でも、MCP が 1 回だけコードなしの結び直しを試す（`stdio.ts` の `store.setRecover`、60 秒は再試行しない）。通れば購読も張り直される。
- 【事実】`tokenExpired`（期限切れ）は対象にしない（`docs/plugin.md` 237 行）。
- 【事実】再起動の直後に 401 になる経路は、コードを読んだ範囲では特定できていない（`CHANGELOG.md` #185 の項）。

### 経路 C: 購読が途切れたまま idle 期限で切れた【事実＋推測】← #254 に一番近い

- 【事実】購読がない状態で `bindIdle`（既定 60 分）が過ぎると、`expiredReason` が `idle` を返し、`expire` がトークンを失効させる（`credentials.ts` 254〜305 行）。失効の印が残り、以後は `tokenExpired`。
- 【事実】失効したあとは、`rebindNodeToken` が `hasBindToken` を要求するので（`credentials.ts` 462〜463 行）、**コードなしの結び直しは通らない**。daemon は `rebindRejected` で拒み、受信箱に「紐付けをやり直して」（`rebind`）を出す（#186。`server.ts` 1954〜1965 行、`compose.ts` `noticeRebind`）。
- 【事実】親（統括）が `node_bindCode` を呼ぶと、daemon は子の作業ツリーの git のディレクトリにコードのファイルを書く（`bind-handlers.ts` 235〜251 行 `cliIssueFile`）。応答の文は「子に `child_bind` を引数なしで呼ばせる」（同 `cliRebindInstruction`）。
- 【事実】そのファイルを読んで使うのは、`child_bind` を引数なしで呼んだとき（`stdio.ts` 425〜453 行）だけ。**MCP は、ファイルが現れたかを見ていない**。
- 【事実】`node_send` の指示は記録に置かれるだけで、daemon は子を呼ばない。手の空いた子にすぐ届くのは、子の MCP が購読で受けて受信箱のソケットに 1 行を書くときだけ（`docs/plugin.md` 100 行、`notify-socket.ts`）。この経路の子は、その購読が途切れている。
- 【推測】#254 は、(1) MCP のつなぎ直しなどで購読が途切れた → (2) 約 1 時間で idle 失効 → (3) 親の `node_send`・`node_bindCode` は届かない（購読なし・ファイルを読む主体なし）→ (4) 人が `claude attach` で `child_bind` を打つまで止まった、の順。(1) の原因（何が購読を切ったか）は、記録が手元にないので特定していない。#208 の「検証のときに紐付けが外れた本当の原因は未特定」と同じ未特定の部分。
- 【推測】`docs/dev-orchestration.md` 13 行は「背景のセッションは、手が空くと約 1 時間で止まる」と書く。もし手の空いた子のセッションごと止まる（MCP のプロセスも終わる）なら、(1) の原因の候補になる。この場合、`claude attach` で開き直した時点で MCP が新しく起動し、紐付け待ちから始まる。実機で確かめる項目に入れた（§6-4）。

### 経路のまとめ

| 経路 | トークン | 購読 | 結び直しの入口（いま） | 手の空いた子が戻るか（いま） |
|:--|:--|:--|:--|:--|
| A: つなぎ直し | 有効 | なし | 子の AI の `child_bind` | 戻らない（親の `node_send` が届かない） |
| B: 401 | 有効 → 拒まれる | あり → 止まる | MCP が自分で 1 回（#185） | 通れば戻る。通らなければ A・C と同じ |
| C: idle 失効 | 切れた | なし | 親の `node_bindCode` ＋ 子の AI の `child_bind` | 戻らない |

## 2. #145・#185 の結び直しを広げられるか（受け入れ基準 2）

### いまの守り【事実】

`POST /v1/bind` のコードなしの経路（`server.ts` 1954〜1988 行）が通る条件は、すべて合うこと:

1. 作業ツリーの確認（`bindWorktreeOk`。cwd の実パスがそのノードの作業ツリー）。
2. session_id の衝突がない（`bindSessionOk`）。
3. `rebindOk`: Desktop の子でなく、最初に**コードで**紐付けたときに記録した session_id と合う（`compose.ts` 2317 行 `sessionBindings.matches`）。
4. ノードが子ロールでトークンを持てる状態（`checkPrincipal`）。
5. 今も有効な bind のトークンがある（`rebindNodeToken` → `hasBindToken`）。発行の時刻を引き継ぎ、期限は延びない。

失敗は、コードが無効なときと同じ 401 で、全体のスロットルと接続元ごとの上限で数える。

### 広げ方 1: MCP が起動した直後に、自分でコードなしの結び直しを試す（経路 A を直す）

- 内容: `openPendingStdioSession` で、印のノード ID と `CLAUDE_CODE_SESSION_ID` があるとき、入れ物が空のまま起動したら、`rebindChild`（既存）を 1 回呼ぶ。通れば `adopt` と同じ処理（`store.set`）で購読も始まる。失敗のときは、#185 と同じく 60 秒は試さない。
- 守りへの影響: **サーバー側の条件は 1 つも変えない**。変わるのは、「子の AI が呼んだとき」が「MCP が起動したとき」にも増えることだけ。session_id・作業ツリー・ノード ID・有効なトークン・期限を延ばさない、はそのまま。
- 注意（【推測】）: 新しい子の最初の起動では、まだコードで紐付けていないので記録がなく、`rebindOk` は偽になり、`rebindRejected` が出る。その結果、daemon が `onBindInvalid` を呼んで受信箱に「紐付けをやり直して」を出してしまう（`server.ts` 1958〜1959 行）。**最初の起動（コードのファイルがあるとき）は、この自動の結び直しを試さない**ようにする（コードのファイルがあれば、それを先に使う）。さもなければ、毎回の起動で偽の知らせが 1 件出る（ノードごと 10 分に 1 件の間引きはある〔`compose.ts` `REBIND_NOTICE_MS`〕が、増やさないほうがよい）。
- 失敗の記録: 試して失敗したことを、MCP のログ（`childRebindFailed`）に出す（既存の形）。

### 広げ方 2: 紐付け待ちの間、定期的に結び直しを試す（経路 A・B を直す）

- 内容: 入れ物が空で、印がある間、一定の間隔（例: 60 秒。#185 と同じ間隔）で、`rebindChild` を試す。コードのファイルが現れたかも同時に見る（§3 の案 1 の (b)）。
- 守りへの影響: 広げ方 1 と同じ。**攻撃面は、試す回数が増えるだけ**で、失敗は daemon 側の上限（スロットル）で数える。daemon が落ちているときは `daemon_unreachable` を返すだけで、トークンの扱いは変わらない。間隔と上限（試行回数・長い間隔への切り替え）を決めて入れる。
- 注意: 上限のスロットルを MCP の定期の確かめが食い尽くして、本物のコードでの紐付けを 429 にしないこと（`child-bind.ts` の `rate_limited`）。間隔を長めにし、429 を受けたらさらに待つ。

### 広げ方 3: コードなしの結び直しを、idle 失効のあとにも通す（経路 C を直す）

- 内容: daemon 側で、bind のトークンが idle で失効したあとも、一定の猶予（例: 発行から `bindAbsolute` まで）は、session_id・作業ツリー・ノード ID が合えば、トークンを出し直す。
- 守りへの影響: **大きい**。現在の「使わなければ切れる」は、**使われていないセッションのトークンを残さない**ための守り（#189 の趣旨）。session_id は秘密ではない（`docs/plugin.md` 246 行）ので、idle で切れたあとも session_id だけで取れると、同じ OS のユーザーの別のプロセスが、期限切れのあとでも、ノード ID・session_id・作業ツリーを知っていれば取れる。切れる時間が実質 24 時間になる。
- 推奨しない。人（利用者）の許可を挟む形（案 3）のほうが、守りを弱くしない。

### 広げ方 4: コードのファイルが現れたら、MCP が自分で使う（経路 C を直す）【推奨】

- 内容: 入れ物が空で、印があるとき、MCP が、`readCodeFile`（既存。`bind-code-file.ts`）で、定期的に（広げ方 2 と同じ間隔）コードのファイルを確かめる。読めたら、`bind`（`child_bind` の本体）と同じ処理で使う。
- 守りへの影響: **コードそのものの扱いは変わらない**。親の `node_bindCode`（統括の権限）でしか出ない・一度きり・期限つき・0600・持ち主・リンクでない・daemon の ID の一致（`bind_daemon_mismatch`）・作業ツリーの確認、はいまの `child_bind` と同じ。変わるのは、「子の AI が `child_bind` を呼ぶ」が「ファイルが現れたら MCP が呼ぶ」になるだけ。親が人の許可を得てコードを出す、という手続きの意味は変わらない。コードを会話・報告に出さない点も同じ（MCP のメモリの中だけ）。
- 注意: コードのファイルは、最初の起動のときも現れる（`touryou child` の起動の前に daemon が書く）。起動の最初の番で子の AI が `child_bind` を呼ぶのと、MCP が自分で使うのが競合する。コードは一度きりなので、片方が先に通れば、もう片方は `bind_code_used`（または、ファイルが消えていて「ファイルがない」）になる。`bind` の中で、入れ物に値が入っていれば `whoami` で成功を返す（呼び出し側が失敗と取らない）形にする。
- 注意: ファイルの存在を調べる頻度。MCP が `.git` のファイルを読むだけで、daemon は叩かない（ファイルがあるときだけ daemon に送る）ので、試行の頻度は上限に影響しない。

## 3. 設計案（受け入れ基準 4）

2 段にしたい、という issue の整理に合わせて、段ごとに比べる。

### 段 1: MCP が自分で紐付けを戻し、購読を再開する

#### 案 1-A: MCP の起動直後と定期の確かめで結び直す（広げ方 1・2・4 の組み合わせ）【推奨】

- 内容:
  - (a) 紐付け待ちで開いたとき、コードのファイルがなく、印とセッションの ID があれば、コードなしの結び直しを 1 回試す。
  - (b) 紐付け待ちの間、60 秒ごと（間隔は設定可）に、コードのファイルの有無を確かめ、あれば使う。ファイルがなければ、コードなしの結び直しを、間引いて（例: 失敗するごとに間隔を倍にし、上限 10 分）試す。
  - (c) 結び直しが通ったら、購読を張り直す（既存の `follow`）。続けて、**受信箱のソケットに、固定の 1 行（「touryou の受信箱（inbox_fetch）を読んで」の形。既存の `notificationText`）を、MCP が 1 回だけ自分で書く**。新しいプロセスの購読は「今より後」から始まる（`node-subscriber.ts` 239〜243 行）ので、結び直しの前に積まれた指示は通知されない。この 1 行が、手の空いた子を起こす（§4 の経路 W3）。
- 難易度: ★★★☆☆ (3)。MCP の中だけの変更で、daemon の API・守りは変えない。試験は、タイマーと入れ物を差し替えられる作り（`deps.sleep`・`deps.fetch`・`deps.codeFile`）で書ける。
- 有効度: ★★★★☆ (4)。経路 A・C（コードが出された場合）が、人も子の AI も打たずに戻る。経路 C は、親（統括）が `node_bindCode` を出す手間は残る（段 2）。
- 残る課題: MCP のプロセスが止まっている場合（経路 C の推測の (1) の原因が「MCP が終わる」なら）は、プロセスが動かないので、この案は効かない。§6-4 の実機の結果次第。

#### 案 1-B: 結び直しは起動直後の 1 回だけ（広げ方 1 だけ）

- 内容: 案 1-A の (a) だけ。定期の確かめ・ファイルの監視はしない。
- 難易度: ★★☆☆☆ (2)。
- 有効度: ★★☆☆☆ (2)。`claude attach`・`/mcp` の Reconnect のあと（経路 A）は戻る。起動のときにまだコードのファイルがない場合（idle 失効のあとに親が出し直す場合。経路 C）は戻らない。
- 向き: 経路 A だけを直したいとき。

#### 案 1-C: daemon が idle 失効のあとにも結び直しを通す（広げ方 3）

- 内容: §2 の広げ方 3。
- 難易度: ★★★★☆ (4)。トークンの期限の設計（#189・#198）と、失効の印（`expiredHashes`）の扱いを変える。
- 有効度: ★★★★☆ (4)。経路 C も、親の手なしで戻る。
- 守りへの影響: 大（§2）。**推奨しない**。

### 段 2: 戻らないとき、統括が利用者に「問題と、直してよいか」を聞いて直す

#### 案 2-A: 既存の `node_bindCode` ＋ 案 1-A の自動で使う、統括の手順の整備のみ（新しい道具なし）【推奨】

- 内容:
  - 統括の受信箱の知らせ（`bindLostSuspect`・`tokenExpiredIdleBind`・`rebind`。`packages/core/src/inbox-messages.ts`）の「次にすること」の文を、「`node_send` で `child_bind` を呼ばせる」から、**「利用者に、問題（子 X の紐付けが切れた）と、直してよいか（`node_bindCode` で紐付けのコードを出し直す）を聞く。承認が出たら `node_bindCode`。子の MCP が自分でコードを使う」**に変える。状態画面のカードの文（`packages/daemon/src/ui/app-text.ts`）、`docs/plugin.md` 100〜101 行、統括の skill（`plugin/skills/integrator/SKILL.md`。ここは読んでいない）も合わせる。
  - 利用者への質問は、統括が `AskUserQuestion` でする（人の判断を挟む。コードは会話に出ない）。
- 難易度: ★★☆☆☆ (2)。文面と手順の変更。案 1-A が前提。
- 有効度: ★★★☆☆ (3)。人の許可が要るので、完全な自動ではないが、「人が `claude attach` で打つ」は不要になる。
- 守りへの影響: なし。`node_bindCode` は統括の権限（自分の子孫）のままで、人間のロールだけの操作は増えない。

#### 案 2-B: 統括向けの新しい道具（例: `node_repairBinding`）

- 内容: 利用者の承認を引数にとり（`approvedBy`）、daemon が、状態を確かめて、`node_bindCode` を出し、子の MCP を促す。診断（トークンの有無・購読の有無・最後の使用の時刻）を、1 回の応答で返す。
- 難易度: ★★★★☆ (4)。daemon のハンドラ・core の契約（`contract.ts`）・MCP の道具・skill・試験を足す。
- 有効度: ★★★☆☆ (3)。診断が見える分、統括の判断は楽になるが、できることは案 2-A と同じ。
- 守りへの影響: 道具が増えるぶん、「承認の証拠」を何で確かめるかの設計が要る（daemon は人の承認を確かめられない。自己申告になる）。**自己申告の承認は、守りにならない**ので、案 2-A のように、統括の `AskUserQuestion` と `node_bindCode` の権限の線引きのままのほうがよい。

### 組み合わせの比較

## 4. 親から手の空いた子を起こす経路の候補と、安全面（受け入れ基準 3）

「起こす」には 2 つの意味がある。(i) 子のセッションに番を始めさせる（受信箱を読ませる）。(ii) 子の MCP の紐付けを戻す。段 1 の案 1-A は、(ii) を MCP だけで済ませ、(i) は MCP が自分の受信箱のソケットに書く（W3）。

| 経路 | 内容 | 状態 | 安全面 |
|:--|:--|:--|:--|
| W1: 名前宛ての `SendMessage`（統括から子へ） | 統括（Claude Code）が、`claude --bg` の名前（`orch-work-…` など）を宛先に送る（`docs/dev-orchestration.md` 13 行は、統括と手伝いがこの経路でやり取りしている）。手の空いた子の番を始めるかは**実機で未確認** | 実機で確かめる（§6-1）。touryou の daemon は関与しない | 文は統括が書く。**コード・トークンを文に入れない**ルールを守る（`cliRebindInstruction` は、コードを入れない作り）。子が従うかは、子の AI の判断。紐付けが外れた子は、touryou の道具が使えず、`SendMessage` は子の範囲の許可（`hook-policy`）で拒まれうる（`plugin/skills/child/SKILL.md` 43 行が「`SendMessage` などが拒否されても、自分で原因を探さない」と書く） |
| W2: daemon から子のセッションへ、daemon の知らせ | daemon が、子の受信箱のソケットに書く | 現状できない。ソケットの場所は子のプロセスの環境変数（`CLAUDE_CODE_MESSAGING_SOCKET`）で、daemon は知らない。MCP は子のロールの認証の前は、daemon に何も送れない（紐付け待ちの MCP は、根のトークンを持たない） | 新しく「ソケットの場所を MCP が daemon に申告する」道を作ると、**認証の前の入力**になる（偽の場所を書かれうる）。**非推奨** |
| W3: 子の MCP が、自分の受信箱のソケットに、固定の 1 行を書く（結び直しが通ったあと） | 案 1-A の (c)。`notificationText` と同じ文（「touryou の受信箱（inbox_fetch）を読んで…」） | 購読が張れているときの既存の動きと同じ（`stdio.ts` の `notify`）。手の空いたセッションを実際に起こすかは §6-3 で確かめる | **一番安全**。書くのは自分の MCP が自分のセッションに。固定の文でコード・トークンを含まない。daemon との新しい道もなし。結び直しが通ったときだけ 1 回 |
| W4: 統括向けの新しい道具（診断・再起動の依頼） | 案 2-B | 新規 | 承認の証拠が自己申告になる。人間のロールだけの操作（`claude attach`・`claude stop` など）を AI の道具に移すと、人の許可の線が曖昧になる。**非推奨** |
| W5: 統括が `claude --bg` で子を開き直す・`claude attach` を自動で打つ | 統括が、手元の Mac のコマンドで、子を起こす | 対話の端末（attach）は人の操作で、統括が自動で打つのは、人の操作の代行になる | **人間のロールだけの操作を増やさない**に反する。**非推奨** |

結論: 起こす経路は、**W3（MCP が自分に書く）を主**、W1（`SendMessage`）は**補助の候補**（実機で効くと分かれば、段 2 の統括の手順の中で「承認後に使える手」の 1 つにする）。W2・W4・W5 は、安全面で採らない。

## 5. 推奨と、実装の分け方（案）

推奨: **案 1-A ＋ 案 2-A**。

実装の分け方（別の子に切る単位。この調査では実装しない）:

1. `packages/mcp`: 紐付け待ちの自動の結び直し（起動直後・定期・ファイルの監視）と、結び直しのあとの 1 行の通知。`child_bind` との競合の扱い（§2 の広げ方 4 の注意）。試験は、タイマー・ファイル・`fetch` を差し替えて書く。
2. 文面: `packages/core/src/inbox-messages.ts`（`bindLostSuspect`・`tokenExpiredIdleBind`・`rebind` の「次にすること」）、`packages/daemon/src/ui/app-text.ts`、`docs/plugin.md`、`CHANGELOG.md`、統括の skill。統括が、利用者に「問題と直してよいか」を聞く手順を書く。
3. 原因の特定（経路 C の (1)）: 実機の記録（MCP の標準エラーの `subscribeWaitingForBind`・`childRebindFailed`・`stdioClosed` の時刻）を、次の再現で取る。案 1-A の入れた MCP のログに、紐付け待ちに入った理由（起動・401・退役）を 1 行足すと、次回から特定できる。

守りの確認（実装の子への注意）:

- サーバー側（`POST /v1/bind`・`rebindNodeToken`・`expiredReason`）の条件は変えない。
- コード・トークンを、会話・報告・ログ・失敗の原因に出さない（既存の規則）。
- 子の AI に新しい道具を足さない。人間のロールだけの操作（`claude attach`・`claude stop`）を AI が代行する道を足さない。
- 最初の起動で、偽の「紐付けをやり直して」を出さない（§2 の広げ方 1 の注意）。

## 6. 統括が実機で確かめる項目（受け入れ基準 5。子は実機で確かめない）

準備の共通: 統括の daemon が動いていて、CLI の子（`claude --bg`）が 1 つ、紐付け済みで、手が空いた状態（`report_progress` を出したあと、番が終わっている）。コード・トークンは、ログや会話に書き写さない。

### 6-1. `SendMessage` が手の空いた子を起こせるか

1. 子を、紐付け済みの手の空いた状態にして、`claude agents` で名前を確かめる。
2. 統括のセッションから、`SendMessage` で、その名前に「touryou の受信箱（inbox_fetch）を読んで」を送る。
3. 子のセッションで、番が始まり、`inbox_fetch` が呼ばれるかを見る（`claude attach <名前>` は、見るだけ。何も打たない）。
4. 紐付けを外した状態（下の 6-2 の状態）でも、同じことをする。紐付けが外れた子は、`SendMessage` の許可（範囲）で拒まれるかも見る。
- 期待（仮説）: 紐付け済みなら起きる。外れた状態では、番は始まるが、touryou の道具は `child_bind` と `whoami` だけで、結び直しは子の AI の呼び出しに依存する。
- 記録: 起きた・起きなかった・拒まれた、の 3 つ。時刻と、子の `claude agents` の表示。

### 6-2. 紐付けを外した状態の作り方（再現）

1. 子を紐付け済みの手の空いた状態にする。
2. 経路 A: 子のセッションを `claude attach <名前>` で開いて閉じる（MCP がつなぎ直される）。
3. 経路 C: 経路 A のあと、約 1 時間以上、何も打たずに置く（`bindIdle` の既定は 60 分。確かめを早めたいときは、設定 `tokenExpiryMinutes.bindIdle` を一時的に短くして daemon を再起動する。**設定を戻す**）。
4. 統括の受信箱に、`bindLostSuspect`（15 分後）→ `tokenExpiredIdleBind`（idle 失効後）が出るかを見る。
5. 状態画面の子のカードの札と、MCP の標準エラー（`subscribeWaitingForBind` など）の時刻を取る。

### 6-3. MCP が自分の受信箱のソケットに書くと、手の空いたセッションが起きるか

- 紐付け済みで購読が張れている子の手が空いたとき、親が子に `node_send` を送ると、子の MCP が受信箱のソケットに 1 行を書く既存の動きがある。この動きで、手の空いた子の番が始まるかを見る（`stdio.ts` の `notified` のログと、子の画面）。
- 手順: (1) 子を手の空いた状態にする。(2) 統括から、`node_send` で子に、指示を 1 つ送る。(3) 子の MCP の標準エラーの `notified` と、子の画面（`claude attach`。見るだけ）で、番が始まったかを確かめる。
- 期待: 始まる。これが効くなら、案 1-A の (c) も効く。効かないなら、案 1-A の (c) は、`inbox_fetch` の未読の促し（Stop のフック）に頼る形に変える必要がある。

### 6-4. 背景のセッションが約 1 時間で止まるとき、MCP のプロセスはどうなるか

- `docs/dev-orchestration.md` 13 行は、背景のセッションが、手が空くと約 1 時間で止まる、と書く。子（`orch-work-` ではない touryou の子）も止まるのか、止まったときに MCP のプロセスも終わるのかを確かめる。
- 手順: (1) 手の空いた子を、1 時間以上置く。(2) `claude agents` の表示（止まったか）と、`ps` で、その子の MCP（`touryou-mcp --stdio`）のプロセスが残っているかを見る。(3) `claude attach` で開いて、MCP がつなぎ直されるか（`stdioConnected` のログ）を見る。
- 期待: 不明。止まって MCP も終わるなら、案 1-A は効かない（プロセスがない）。そのときは、別の設計（daemon 側で子を再起動する道。これは `claude --bg` を daemon が管理していない現状では、設計の大きな変更）が要る。

### 6-5. attach のあとの `CLAUDE_CODE_SESSION_ID`

- 既存の項目（`docs/manual-verification-checklist.md` A4-3）。違えば、コードなしの結び直し（案 1-A の (a)）は効かない。子が `child_bind` を引数なしで呼んで通るかで確かめる。
