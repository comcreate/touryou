# 1. 作業の種別と理由

- **種別：新機能（小）**。成果物は、仕様（touryou-ui.md）・設計の下書き（本書）。タスクと決定ログは、実装の着手時に作る。
- 理由：
  - 変えるのは、既存の機能（状態画面）の描画の層だけ。daemon の API・表示モデル（`ui-view.ts`）・保存先を変えない。
  - 影響は、`packages/daemon/src/api/ui-assets.ts`、`packages/daemon/src/ui/*` の中に収まる（単一のモジュール）。
  - 新しい業務領域・外部システムとの連携は無いので「大」ではない。
- 「破壊的変更」にしなかった理由：利用者が呼ぶ公開の API・コマンド・設定の形は変わらない。ただし、画面の保存キーと図の配置の定数の扱いは 6 節で決めてもらう。
- 決定ログ（adr）は、6 節の決定が出たあとに追記する。決まっていないものを先に書かない。
- PRD は書き換えない。FR_021 は画面の存在を求めるだけで、見た目の細目はない（【推測】全文は未読）。

- 【未確認】：ブラウザで見ていない。本書の見た目に関する記述は、すべて読み取りであり、ブラウザで確かめていない。

# 4. 設計の方針（案）

1. **描画の層だけを変える**。表示モデル・API・保存キーは変えない（UI_104・UI_103）。
2. 窓とタブは、画面の中だけの状態（記憶しない）。どのタブを選んだかは localStorage に書かない（UI_010）。
3. 図は、【推測】既存の `graph-*.ts` の配置と線の経路を作り直す形になる。配置の関数 `layoutOf` は純粋関数で、親が見えないノードや輪の扱い（`layout.test.ts` の 4 本目・5 本目の試験）は、見本にも必要な性質なので保つ。
4. 見本のインラインのスクリプトとスタイルは、そのままは使えない（CSP が同じ配信元だけ、`style` 属性なし）。本番の `UI_CSS`・`UI_JS` の文字列に移す。見本の中の作り物のデータと操作は捨てる（UI_101）。
5. 実装は、窓の骨組み（ヘッダー・窓・タブ・幅の区切り）→ 色とスクロールバー → 図 → カードと省略 → 設定の窓 → 文言、の順に小さく分けられる【推測】。

# 5. 実装の子へ渡す観点

- 各受け入れ基準（touryou-ui.md の 5 節）を、試験またはブラウザでの手順に結びつける。ブラウザでの確認は、既存の `browser`・`real-ui` の試験の仕組みで足りるか、実装の子が読んで決める【未読】。
- 見た目の確認は、明・暗・スマホ幅・日本語と英語・キーボード・動きを止める設定で行う。

## 6-1. 図の作り方（箱の寸法・配置の定数）

| A（推奨：見本に忠実） | 図を見本どおりの SVG 一枚で描き直す。`graph-layout.ts` の定数を見本の値（箱 150×64、列 460、行 84）に替え、`layout.test.ts` の固定値も同時に更新する | ★★★★☆ | ★★★★★ |
